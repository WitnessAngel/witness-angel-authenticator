# Review of the Witness Angel Authenticator specification

Scope: `README.md`, `01-architecture-and-platform.md`, `02-ux-and-screens.md`, `03-business-logic.md`, `04-data-and-protocols.md` (spec v1.5).
Method: full read of the five files, then spot checks against the source in the sibling checkouts (`witness-angel-components` on `wakeygen_stable` @4ebc5d2, `witness-angel-cryptolib` on `poc/pure-python-crypto-utils` @85b5dc7, `witness-angel-server` on `dev` @093fd65), plus the shipped `bin/authenticator-1.5-…-release.aab` (`base/assets/private.tar`).

## Overall verdict

**Good, nearly sufficient, but not yet ready to hand to a reimplementer.** The spec is unusually thorough. It has real byte-level examples (metadata file, ASN.1 dump, JSON-RPC envelope, cipherdict), exact gateway acceptance rules taken from the server, and honest open-issue lists. The core crypto and protocol claims I checked are correct.

Three kinds of problem remain:

1. **The source baseline is wrong or unstated.** The spec does not say which code revision it describes, and its one claim about that is wrong (the cryptolib is on a POC branch, not `wakeygen_stable`). The gateway serialises JSON with pymongo `bson.json_util`, not the vendored `extjson` the spec describes as "the same helpers".
2. **The files contradict each other on several points a reimplementer would act on.** Examples: passphrase trimming, whether the crypto fallback backend is used on all OSes, whether keygen shows the spinner, gateway URL validation, Android USB discovery, and FR translations. 02 is wrong more often than 03 and 04.
3. **There is no normative layer outside 01 Part A.** Four separately numbered open-issue lists (66 items, many duplicated) never say whether a reimplementation must keep, may fix, or must fix each item. There are also no test vectors to prove interoperability.

There are no hard blockers for on-disk or wire interop: the formats in 04 are right. But the items marked **major** below would each cost a reimplementer a wrong guess or a debugging session.

Severity scale: **blocker** = cannot implement interoperably without guessing; **major** = likely wrong implementation or wasted effort; **minor** = polish.
